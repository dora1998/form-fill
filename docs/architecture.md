# アーキテクチャ

入力経路は content → popup → background → native です。分類とプロフィールの読み出しを分け、認証後の値合成はネイティブで行います。通常のメニュー起動では解析・認証付きプレビュー・再認証付き入力、ページ内ボタンでは信頼されたpopupを開き、解析・一回の認証・入力を行います。

## 責務と依存方向

Swift はローカルの `Packages/FormFillKit` にまとめます。

- **FormFillCore**: プロフィール、欄・分類・入力計画の型、決定的なルール、住所構成、値合成、診断データの変換。OS認証、Keychain、Foundation Modelsを呼びません。
- **FormFillApplication**: 分類の進行、認証付き入力セッション、プロフィール編集と診断保存の処理手順。外部作用は小さなclientやclosureで受け取ります。
- **FormFillApple**: Foundation Models、LocalAuthentication、Keychain、App Groupの実装。CoreとApplicationに依存します。
- **App**: SwiftUIの描画と操作通知、実装の組み立て。編集状態と非同期結果の世代管理は画面から分離します。
- **FormFillBridge**: Safariの要求を検証・変換し、Applicationに渡して結果を通信形式に戻します。SafariServicesに依存しないrouterとして独立に検証します。Safari固有のcontext処理だけをExtensionターゲットに残します。

TypeScriptは単一npm packageです。wire型とdecoder、browser APIの接続、popupのworkflowと描画、contentのDOM操作とsnapshot、通常診断と詳細収録を分けます。DOMノードを持つ型は通信型に含めません。ブラウザlistenerの登録は起動部分で行い、処理本体は依存を渡して作れます。

## 通信契約

`version`、要求の種類、`requestID`を持つ通信データを境界で検証します。解析・プレビュー・入力・取消の応答型を区別します。Swift内の分類結果と入力計画は型付きで扱い、処理間で辞書化して再decodeしません。

`Tests/Contracts/analyze-requests.json` はTSとSwiftが共用する受理・拒否の合成fixtureです。型宣言だけでは外部入力を検証できないため、実行時の検証も維持します。保留理由は安定した `reasonCode` で渡し、表示文言を診断の識別子に使いません。既存の `reason` は表示互換用です。

検証は各信頼境界で必要です。共通化によって送信元の確認、nativeの要求検証、入力直前のDOM再確認を省略しません。

## 分類と値合成

分類器は登録プロフィールを受け取りません。ルールで判定できる欄を確定し、曖昧な欄をモデルへ送り、構造化結果を検証します。住所の構成は同じグループの欄だけを使って判断し、モデルの返した順番で住所要素を並べ替えません。

モデルclientと時計を注入し、部分的な失敗、不正な出力、再評価の棄却、期限超過を実モデルなしで検証します。モデルの利用可否、生成スキーマ、SDKエラーの変換はApple側の実装が担当します。バッチ間の期限確認と実行中の生成停止は別の契約です。

値合成器は選択済みのプロフィールを明示的に受け取り、分類とサイト側の制約から値と保留理由を作ります。ダミープロフィールはテスト専用です。旧 `analyzeInline` 経路は提供しません。

## 状態と認証の所有者

Popupのworkflowが解析・グループ選択・認証待ち・プレビュー・入力・取消の状態を所有します。表示のhidden/disabledを状態の代わりに使いません。時計と通信を差し替え、取消・再解析・期限後の遅い応答を検証します。

ネイティブの入力セッションはactor内の一時状態です。タブ、origin、request ID、プロフィールID/revisionと結び付け、入力値を返す前に消費します。プロセス再起動で失効します。通常入力のプレビューと入力ではそれぞれ新しい認証を行い、quick入力では一回の認証を行います。取消時の認証context無効化と認証後の期限再確認を保持します。

Appの編集モデルは画面のロックと古い非同期結果の破棄を担当します。認証成功を共有のBoolに置き換えず、認証とKeychain読出しには同じ認証contextを使います。UIへの結果反映を破棄することと、実行中の保存を取り消すことを混同しません。

## DOMとsnapshot

ContentがDOMノードとfield IDの対応を所有します。グループ選択後のIDを診断側で全ページの順番から推測しません。通常の抽出と診断は、値を読まない構造・ラベル・候補判定を共用します。

診断collectorは共通DOM処理を含む独立bundleとして注入します。`executeScript`に渡す関数は自己完結させ、別のJavaScript実行環境のimportやclosureを参照させません。対応するsnapshotがない場合はIDを推測せず未対応として扱います。

SnapshotはURL、ノード、メタデータ、既存値、期限に結び付けます。入力計画の受領時だけでなく、値の設定直前にもDOMを検証します。入力イベントでサイトが別の欄を更新する場合があるため、書込み間の再確認も必要です。フォームは送信しません。

## 診断と保存

通常の診断はallowlistから再構築し、現在値、ラベル原文、任意の例外文字列を出力しません。明示的に有効にした詳細収録は別の経路です。

詳細ログ保存は、サイズ・形式検証、OS認証、登録プロフィールのマスキング、保存の順で行います。認証失敗時は保存しません。永続化にはマスキング済みを表す型を渡し、保存・一覧・読出し・削除をrepositoryに集約します。

マスキングは現在の登録プロフィールと一般的な表記のベストエフォート処理です。他人の情報、未知の表記、DOMに埋め込まれた認証情報まで匿名化できるという保証ではありません。App Groupのファイル保護、バックアップ除外、一時ファイルからの公開を保持します。

## 検証

純粋なルール・通信契約・workflow・編集モデル・保存手順は決定的な単体テストで確認します。DOMの抽出・イベント・サイト側の変更は既存のWebKitテストで確認します。Foundation Modelsの精度評価は合成フォームの実モデル評価として別に実施します。

署名なしiOSビルドは構成とコンパイルの確認です。共有Keychain、Safariからの認証、端末ロック時の挙動は実機で検証し、単体テストやビルド成功で代替しません。
