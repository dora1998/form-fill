# プロダクト仕様（初期案）

状態: 固定のダミープロフィールでSafari上の入力を試す最小実装を追加済み。以下の保存・プロフィール編集・リリース受入条件は今後の仕様を含む。

確定した方針: 初期版は非対応端末を対象とせず、1プロフィールから始める。内部設計は後から複数プロフィールへ拡張できるものとする。その他の項目は引き続き初期案である。

## 目的

日本の姓名・住所入力フォームに対し、Safari 上の操作で適切な項目へ一度で入力できる iOS アプリをつくる。住所全体を番地欄へ入れる、都道府県の選択肢に対応できない、姓名の分割を間違える、といった既存の自動入力の修正作業を減らす。

個人情報と入力処理は端末内で扱う。LLM はフォームの意味を推定する補助に用い、姓名・住所の実値を LLM へ渡さない構成を第一候補とする。サイトへ情報を入力した後は、そのサイトのスクリプトが値を読み取れる。この境界を操作前に分かるようにする。

## 最初の開発成果物

- 空の SwiftUI iOS アプリと Safari Web Extension の Xcode プロジェクト構成。
- Safari のポップアップ、バックグラウンド、コンテンツスクリプトとネイティブハンドラーの疎通。
- この仕様とアーキテクチャ、実機で検証する項目。

この段階ではプロフィール保存、モデル推論、フォームへの個人情報入力は実装済みと扱わない。後述の MVP は次の開発対象である。

## 対象ユーザーと利用手順

日本の通販、会員登録、配送先入力を Safari で行う利用者を想定する。MVP ではひとつの本人プロフィールを扱う。

対応範囲はiOS 26以降のApple Intelligence対応端末とする。Foundation Modelsの利用に必要な有効化・モデル準備状態を確認する。非対応端末向けのルール専用版や代替モデルは今回の対象外とする。

プロフィールの追加・切替UIはMVPに含めない。内部では安定したプロフィールIDを使い、保管形式を複数件対応とし、選択中IDをプロフィール内容と分離する。初期版の1件制限は登録処理で適用し、分類器・値合成器・保存方式には1件という前提を埋め込まない。

1. アプリで姓・名、フリガナ、郵便番号、都道府県、市区町村、町域、丁目・番地・号、建物名・部屋番号を登録する。
2. Safari 設定で拡張を有効にし、必要なサイトへのアクセスを許可する。
3. 入力画面で拡張を開き、利用者が解析を開始する。
4. 拡張が入力項目を分類し、入力予定の項目と値、対象サイトを表示する。判定できない項目は保留する。
5. 利用者が「入力する」を選択すると、表示した項目だけへ入力する。都道府県の選択欄は初期値を上書きする。ほかの既存値は保持する。
6. 入力結果を確認し、フォームの送信は利用者自身が行う。

入力前のプレビューは短く、判定不能や上書き対象を識別できる内容とする。毎回全項目の手作業による対応付けを求めない。

## プロフィールと入力表現

| 保存する要素 | 主な入力先 | 制約 |
| --- | --- | --- |
| 姓・名 | 姓、名、姓名一体欄 | 自動で姓と名を推測分割しない。結合時の空白を明示した設定にする |
| 姓・名のカナ | セイ、メイ、フリガナ一体欄 | 全角カタカナを基本とし、ひらがな指定に変換する |
| 郵便番号 | 一体欄、上3桁・下4桁 | 数字7桁で保持し、欄ごとにハイフン有無を合成する |
| 都道府県 | テキスト、標準 select | 正式名を保持し、選択肢の表示名・値と照合する |
| 市区町村 | 市区町村欄 | 郡・区などを利用者の登録内容のまま扱う |
| 町域 | 町名、住所前半 | 市区町村や番地と混ぜず保持する |
| 丁目・番地・号 | 番地、住所後半 | 郵便住所の文字列表記を保持し、機械的な数値分解はしない |
| 建物名・部屋番号 | 建物、住所最終行 | 空欄を許す。番地だけの欄へ混入させない |

住所1・住所2・住所3などの曖昧なラベルは周辺項目を含めて分類する。境界が判別できない場合は、推測で部分住所を落としたり重複させたりせず保留する。「住所全体」などが明確な一体欄では登録済みの要素を順序どおり結合する。半角・全角、空白、ハイフンの変換はサイトの明示的制約に合わせ、原本を変更しない。

電話番号、メール、パスワード、支払情報、ローマ字氏名、複数配送先は MVP の対象外とする。

## MVP のフォーム対応

- 標準 HTML の表示中・編集可能な `input`、`textarea`、`select`。
- 同一のトップレベル文書で、明示ラベル、`autocomplete`、`name`、`id`、プレースホルダー、周辺見出しを用いた項目判定。
- 姓名の一体・分割、カナ・ひらがな、郵便番号の一体・分割、住所の一体・分割。
- 都道府県の標準 select は正規化した表示名・値で一致する選択肢だけを選ぶ。選択肢の順序を都道府県コードと決めつけない。
- 入力時に必要なイベントを発火し、フォームの変更を検知するサイトで表示値と内部状態が一致することを検証する。

カスタムドロップダウン、クロスオリジン iframe、closed Shadow DOM、CAPTCHA は初期対象外。未対応の構造を説明し、誤入力しない。SPA の DOM 更新や郵便番号からのサイト側住所補完が、計画済み入力と衝突する場合は再解析する。

## LLM とプライバシーの方針

フォーム分類にオンデバイス LLM を用いる。プロフィール値は決定的な処理で組み立てるため、モデルが姓名・住所を創作する余地を減らす。既存の入力値、ページ全文、Cookie、パスワード欄はモデルへの入力から除外する。ラベルや周辺テキストにも個人情報が含まれる可能性があるため、収集量と文字数を制限する。

Apple の Foundation Models を第一の検証候補とする。対応 OS、対応端末、Apple Intelligence の有効化、モデルの利用準備状況、言語、Safari Web Extension のプロセスでの利用可否を確認し、API の利用可能性判定で分岐する。具体的な提供条件は本仕様作成時点で Apple の最新資料・実機による確認が未完了であり、拡張内で利用できると約束しない。

対応端末でもApple Intelligence未有効化・モデル準備未完了・一時的な利用不能があり得る。解析開始前に利用状態を確認し、準備できていない場合は理由と設定・再試行の案内を表示する。非対応端末向けのルール専用モードは提供しない。ルールは対応端末での明確な欄の分類とモデル出力の検証に利用し、推論失敗時は確実に判定できた欄だけをプレビューへ残す。曖昧な欄は保留し、クラウド推論へ切り替えない。拡張内で推論できず、利用者が Safari からアプリへ毎回移動しなければならない場合は、一度で入力できる体験への影響を評価して MVP の構成を再決定する。

プロフィールの保存方式は次段階で決める。候補は共有 App Group 内のファイルと Keychain を用いる暗号鍵管理である。端末ロック時の可用性、バックアップ、削除、拡張との共有を検証し、平文の `UserDefaults`、JavaScript の永続ストレージ、ログには個人情報を保存しない。サイトには入力実行に必要な値だけを渡す。

任意のページテキストを命令として扱わない。LLM の出力は許可された項目分類の構造化データとして検証し、送信・URL 遷移・コード実行などの操作をモデルへ委任しない。ネイティブと拡張間のメッセージも種別・サイズ・フィールドを検証する。

## 受入条件

MVP のリリース判定では、合成プロフィールだけを使った固定のフォーム集で次を確認する。

- 姓名、フリガナ、郵便番号、住所、都道府県 select の各パターンで、期待する入力値と実際の値が一致する。
- 番地専用欄に都道府県・市区町村・建物が入らない。姓名の各欄へ異なる要素が入らない。
- 非表示、無効、読み取り専用、パスワード欄、未対応のカスタム UI へ入力しない。
- 都道府県の選択欄はプレビュー確認後の入力操作で上書きできる。ほかの既存入力は保持する。
- プレビュー後に DOM が変わった場合は古い対応付けで入力せず、再解析または保留する。
- 対応端末でモデル未準備・利用不能の場合は理由を表示して解析開始を保留する。推論失敗・不正な出力では確実に判定できた欄だけを提示し、未判定項目は変更しない。
- 初期版はプロフィールを1件だけ登録でき、編集してもIDを維持する。プロフィールの更新・削除後は古いプレビューの入力を実行できない。
- 自動送信、外部モデルへの通信、個人情報のログ出力がない。
- 機内モードでも、モデルと拡張の実行条件を満たす端末で解析・入力できる。
- 入力成功率、正しい保留率、誤入力率、処理時間をケース別に記録する。数値目標は実機で初期測定後に設定する。

## 未決事項（優先順）

1. 対応端末でのApple Intelligence・モデル準備状態の確認方法と利用不能時の案内。
2. 拡張のネイティブハンドラー内でオンデバイス推論できるか。処理時間・メモリ・停止条件を含む実機検証が必要。
3. 住所要素の登録 UX と姓名結合の空白、よく使う表記の初期値。
4. プレビューの詳細度、上書きの明示操作、保留項目の手動対応付けを MVP に含めるか。
5. 保存暗号化、App Group / Keychain の共有、バックアップ方針、削除 UX。
6. 対応サイト・フォーム集、測定値を基にした精度と待ち時間の目標。

## 開発順序

まず空アプリと拡張の疎通を実機で確認する。同時に Foundation Models の拡張内利用を小さな実験で評価する。その後、合成プロフィールによるルール分類・入力を完成させ、モデル分類を同じインターフェースで追加する。実プロフィール保存は共有・暗号化方式が検証できてから接続する。
